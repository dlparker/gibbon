
* LLM Intent Matching Experiment - Initial Findings

** Experiment Overview

This experiment explored using a local LLM (llama3.1:8b-instruct-q4_K_M)
to match voice-to-text transcriptions to intent categories (IBranch nodes).
The goal was to understand the boundaries and limitations of small models
for this task, and to develop effective prompting strategies.

** Philosophy and Approach

*** Learning with Limited Models

The decision to use a limited model (8B parameters, quantized) was deliberate:

1. Hardware constraint: Currently limited to 4060M GPU
2. Educational value: "I think that I will learn to think about these
   problems better with a limited model. I get to define everything on
   this project, so if I can learn to define well enough to get best
   possible results out of a limited model, my work with better models
   will be more fruitful. I'll make fewer mistakes and better understand
   those that I do make."

This follows Research Lab stage principles - focus on understanding the
problem space rather than achieving production-level results.

*** Finding Boundaries

The experiment specifically aimed to find boundary conditions - cases where
the model's decision could go either way. These boundaries reveal:
- What factors influence the model's choices
- How strongly different signals (keywords, context) affect decisions
- Where the model's limitations lie
- What tuning parameters are available

** Test Setup

*** Categories Hierarchy
- Todo lists (ID=2)
  - grocery shopping list (ID=3)
  - taxes (ID=5)
- Project Notes (ID=4)
  - Customize kanban board app (ID=6)
  - Plan moving out of house (ID=7)
  - Prepare house for sale (ID=10)

*** Test Transcriptions
1. "Get some steaks" - clear grocery intent
2. "get moving boxes" - clear moving/house intent
3. "pack up kitchen" - BOUNDARY CASE (kitchen vs. packing)
4. "email accountant" - inference required (accountant → taxes)

** Progressive Refinements

*** Initial Attempt - Vague Scoring
First prompt used abstract confidence levels:
- 0.9-1.0: "Clearly matched words or phrases"
- 0.7-0.9: "Synonymous words or phrases"
- 0.5-0.7: "secondary or unusual word meanings"

Result: Matched "Get some steaks" to parent category "Todo lists"
instead of specific "grocery shopping list". Too general.

*** Improvement 1 - Concrete Examples
Added specific examples to each confidence level:
- 0.7-0.9: "Specific items that clearly belong to one category
  ('get steaks', 'buy milk')"
- Example: "Get some steaks" → "grocery shopping list" = 0.75

Result: Confidence improved from 0.7 to 0.85 for steaks → groceries.
The model used the example to calibrate its scoring.

*** Improvement 2 - Hierarchy Clarity
Changed category format from indented lists to explicit parent references:
- "grocery shopping list (ID=3, parent: 2)"
- Added rule: "Always prefer the most SPECIFIC category (child over parent)"

Result: Consistently matched to leaf categories instead of parents.

*** Improvement 3 - Global Evaluation
Hypothesis: Model was stopping after finding first match above 0.5 threshold.

Changed from: "Find matches above 0.5"
To: "Evaluate ALL categories first, then return top 2"

Result: Improved some matches but revealed the "pack up kitchen" boundary
case - consistently matched to "grocery shopping list" due to strong
"kitchen" → "groceries" association.

** The Context Weighting Experiment

*** Discovery of the Boundary
"pack up kitchen" consistently matched to "grocery shopping list" with
high confidence (0.75-0.85), despite "pack up" suggesting moving.

This revealed a hard boundary: the word "kitchen" has a very strong
association with groceries/food in the model's training data.

*** Hypothesis: Context Should Help
"I think you are right that the speaker will mostly stay on the same track."

Design decision: Optimize for the common case - consecutive drafts
typically relate to the same topic. Users can learn to say "switch focus"
or "change tacks" when intentionally changing topics.

This follows the 2nd rule of software engineering: "optimize for the
common case."

*** Context Implementation - Iteration 1 (Weak)
Added previous match to context with mild suggestion:
"The last user interaction created this context, so consider it
in your analysis"

Result on "pack up kitchen" with "Plan moving out" context:
- Confidence dropped from 0.85 → 0.65
- Category still "grocery shopping list"

Finding: Context IS influencing the model, but not enough to flip
the decision. The "kitchen" association is weakening but still winning.

*** Context Implementation - Iteration 2 (Strong)
Strengthened context influence:
- "Give STRONG preference to categories related to context"
- "Users typically stay on the same topic for multiple consecutive drafts"
- "Context weight: +0.2 to confidence"
- "Only choose different category if CLEAR, EXPLICIT keywords indicate
  topic change"

Combined with temperature=0 for deterministic results.

Result on "pack up kitchen" with "Prepare house for sale" context:
- Category: "Prepare house for sale" (ID=10) ✓ CORRECT!
- Confidence: 0.70

SUCCESS: Strong context weighting overcame the "kitchen → groceries"
association.

** Key Findings

*** Temperature Matters
Without temperature=0, results were non-deterministic. Same prompt could
produce different answers across runs, making it impossible to evaluate
prompt changes systematically.

With temperature=0: Consistent, reproducible results.

*** Context Weighting Effectiveness
Weak context influence: Reduced confidence in wrong answer but didn't
flip decision.

Strong context influence (+0.2 boost, emphatic language): Successfully
overrode strong word associations.

*** Word Association Strengths
"kitchen" → "groceries" is a very strong association that requires
significant countervailing evidence (context) to override.

This suggests that some word associations in small models are nearly
unbreakable without external signals like context.

*** Model Behavior Patterns
The model consistently returned only 1 result instead of the requested 2,
suggesting it stops when confidence threshold is met rather than
evaluating all options.

With explicit "evaluate ALL categories first" instruction, this improved
but didn't completely solve the issue.

*** Context Continuity vs. Topic Switching
Strong context weighting successfully maintained topic continuity
across related drafts, while still allowing clear topic changes
when keywords warranted it ("email accountant" broke away from
house context to match "taxes").

** Architectural Insights

*** Weight Management System
The success of context weighting (+0.2) suggests a need for a "first class
mechanism for managing weights for prompt components."

Future architecture should support:
- Configurable weight values for different signal types
- Experimentation with weight combinations
- Per-category or per-branch weight adjustments

*** Confidence Score Calibration
The detailed scoring guidelines with concrete examples proved essential.
Abstract descriptions were insufficient.

Template for future scoring guidelines:
- Specific examples for each level
- Quantifiable criteria (word position, keyword match type)
- Domain-specific guidance

*** Topic Change Signals
The system should recognize explicit topic-change phrases:
- "switch focus"
- "change tacks"
- "new topic"
- "moving on to"

These could reduce context weight or trigger category re-evaluation.

** Conclusions

*** What Worked
1. Concrete examples in scoring guidelines
2. Explicit hierarchy specifications
3. Strong context weighting for topic continuity
4. temperature=0 for deterministic evaluation
5. Forcing global evaluation before ranking

*** What We Learned
1. Small models have strong word associations that require significant
   countervailing evidence to override
2. Context weighting is effective but must be calibrated (too weak fails,
   appropriate strength succeeds)
3. Boundary cases reveal model limitations and tuning parameters
4. Non-determinism (sampling) makes systematic evaluation impossible
5. The "optimize for common case" principle applies to prompt design

*** Limitations Discovered
1. Model won't return multiple results reliably despite explicit requests
2. Some word associations may be unbreakable with very small models
3. Prompt length matters - context adds ~550 characters

*** Next Steps
1. Integrate this approach into IBranch matching system
2. Build weight management system for prompt components
3. Add topic-change signal recognition
4. Test with real VTT transcriptions (may have different characteristics)
5. Build feedback loop to refine category descriptions based on
   mismatches
